# 20. Running `meta2lib` on Windows

Status of the Windows side, and the one thing that currently blocks it.

Everything marked `[MEASURED]` was run and its output kept. Everything marked
`[INFERRED]` is reasoning from that evidence. `[UNVERIFIED]` means it is a plan
that has not been executed anywhere.

---

## 20.1 What the device needs before any program can open it

`[MEASURED]` from `lsusb -v -d 2cfa:00f3`:

| property | value |
|---|---|
| `idVendor` / `idProduct` | `0x2cfa` / `0x00f3` |
| interfaces | one |
| `bInterfaceClass` | `0xFF` (vendor-specific) |
| `bInterfaceSubClass` / `bInterfaceProtocol` | `0x00` / `0x00` |
| endpoints | four bulk-IN, **no bulk OUT** |
| link speed | SuperSpeed, 5 Gbps |

`[MEASURED]` The device does **not** implement Microsoft OS descriptors.
`tools/msos_probe.c` (build: `gcc msos_probe.c -o msos_probe $(pkg-config --cflags --libs libusb-1.0)`):

```
string 0xEE: FAILED LIBUSB_ERROR_PIPE
MS OS compat ID: FAILED LIBUSB_ERROR_PIPE
MS OS 2.0 compat ID: FAILED LIBUSB_ERROR_PIPE
iProduct: Meta2
```

The ordinary string descriptors answer normally, so the control endpoint works;
the STALLs are specific to the MS OS feature.

That matters because MS OS descriptors are the mechanism by which a
vendor-specific device gets WinUSB installed by Windows with no INF, no catalog
and no signature prompt. This device does not have them.

`[INFERRED]` No in-box Windows driver matches a single vendor-specific
interface, so on a machine that has never had the Meta SDK the device arrives
with no driver at all. A driver package has to be supplied.

`[INFERRED]` Because there is one interface, the function driver binds to the
device directly. `usbccgp`, which exists to split composite devices into
per-interface children, is not involved.

## 20.2 The driver package we wrote

`meta2lib/driver/meta2.inf`. It installs **Microsoft's own `WinUSB.sys`** as the
function driver for `USB\VID_2CFA&PID_00F3`.

It ships no binary. Every file it installs is already inside Windows and already
signed by Microsoft, so nothing of ours runs in kernel space.

Shape:

- `Class = USB`, `ClassGuid = {36fc9e60-c465-11cf-8056-4445bc7c5199}`
- `AddService = WinUSB, 0x00000002, ...` — the `0x2` is
  `SPSVCINST_ASSOCSERVICE`, the flag that actually associates the service with
  the device node. Without it WinUSB is installed as a service and is not the
  device's function driver.
- `ServiceBinary = %12%\WinUSB.sys` — the in-box driver.
- `DeviceInterfaceGUIDs = {c0ee1632-92f8-44a1-bcff-6013a2369925}`, fixed so a
  native WinUSB client can open the device by GUID. `libusb` does not need it.
- `PnpLockdown = 1` so a class driver cannot silently take the interface back.
- No `CatalogFile` line. A catalog signs the binaries a package installs; this
  package installs none of its own. Referencing a catalog that is not shipped
  fails the install outright, which is worse than a warning.

## 20.3 The blocker, and the way through it: a signed catalog

`[MEASURED]` Windows 10 1809 x64 guest, administrator shell, test signing off:

```
pnputil /add-driver meta2.inf /install
Adding driver package:  meta2.inf
Failed to add driver package: The third-party INF does not contain digital
signature information.
Total driver packages:  1
Added driver packages:  0
```

`[MEASURED]` Test signing does **not** lift this. After `bcdedit /set testsigning
on`, a reboot, and `bcdedit /enum` confirming `testsigning Yes`, the same command
gave the same refusal. The plan of "ship an unsigned INF and tell users the
warning is harmless" is dead on x64 Windows: there is no warning to accept.

`[MEASURED]` SetupAPI's own log (`C:\Windows\INF\setupapi.dev.log`) shows the INF
is otherwise fine - it parses, matches the hardware ID, and is selected as the
best driver. Only the catalog step fails. Two distinct failure codes were
measured:

| condition | code |
|---|---|
| no catalog at all | `0xE000022F` |
| catalog present, but it does not contain the INF's own hash | `0xE000024B` |

`[MEASURED]` The second one is the interesting one. A catalog that hashes only
"the files the package installs" is not enough, because this package installs no
files - the catalog has to hash **the INF itself**. `driver/meta2_mkcat.c` does
exactly that with `CryptCATAdminCalcHashFromFileHandle` +
`CryptCATPutMemberInfo` + `CryptCATPutAttrInfo` + `CryptCATPersistStore`, all
from `wintrust.dll`. No WDK, no `Inf2Cat.exe`, no `makecat.exe` - a probe of the
guest found none of the WDK tools present.

`[MEASURED]` Signing is a throwaway certificate, installed into the machine's own
trust stores, in the same shape libwdi/Zadig uses:

```
cert: "CN=usb\vid_2cfa&pid_00f3 (meta2lib autogenerated)"
      thumbprint F8671468EE2030E503962158D6DD2CDE13E4A73E
installed into LocalMachine\Root and LocalMachine\TrustedPublisher
Set-AuthenticodeSignature -> Valid : Signature verified.
private key destroyed
catalog now: Valid
```

`[MEASURED]` With that catalog, the committed INF installs and binds:

```
pnputil /add-driver C:\Users\hermes\driver\meta2.inf /install
Driver package added successfully.
Published Name:         oem3.inf
Driver package installed.

instance:  USB\VID_2CFA&PID_00F3\5&134707B&0&1
friendly:  Meta 2 AR headset (meta2lib / WinUSB)
status:    OK   problem: CM_PROB_NONE
driver:    {36fc9e60-c465-11cf-8056-444553540000}\0002   inf: oem3.inf
WinUSB service: Running
```

`[MEASURED]` One INF bug was in the way until it was fixed. The class GUID tail
`{36fc9e60-c465-11cf-8056-4445bc7c5199}` - the one that appears in a great many
INF examples - is wrong for this purpose and the install fails with it. The USB
class GUID Windows itself uses ends `{36fc9e60-c465-11cf-8056-444553540000}`.

`[MEASURED]` The vendor driver is real competition: `MetaReader` stages a package
signed `Signer Name: Meta Company` that binds the same hardware ID. Our INF is
dated 2026 against the vendor's 2016, and driver rank picks the newer one, which
is why the device switched without any manual unbind.

## 20.4 What this means for distribution

`[MEASURED]` The self-signed catalog route works **on the machine it was run on**,
because the certificate was placed into that machine's `Root` and
`TrustedPublisher` stores. That is the whole trick, and it is the same trick
libwdi/Zadig plays. It is a development unlock, not a distribution story: nobody
else's machine has that certificate.

`[MEASURED]` Zadig itself was inspected rather than trusted. `zadig.c` (2141
lines, the GUI) contains no command-line handling at all; `wdi-simple.c` is the
scriptable sample libwdi ships. libwdi 1.5.1 source was unpacked and read: the
catalog is built through `wintrust.dll` and signed through `mssign32.dll` with a
throwaway certificate, which is what `driver/meta2_mkcat.c` and
`driver/install-driver.ps1` reproduce.

So the distribution decision is now concrete rather than open:

1. **A real Authenticode certificate.** Sign `meta2.cat`, ship `meta2.inf` +
   `meta2.cat`, one `pnputil` line, no user-visible warning. This is the only
   route that a normal user can complete. Cost and enrolment sit outside the
   repository. `[UNVERIFIED]`
2. **Microsoft attestation signing.** The guest's driver store shows what its
   output looks like: `Signer Name: Microsoft Windows Hardware Compatibility
   Publisher` on the USBPcap package. Needs a Partner Center account.
   `[UNVERIFIED]`
3. **Ship the Zadig/libwdi installer** and let it do the same thing we did here.
   Works, adds a third-party dependency and a GUI step. `[UNVERIFIED]` here -
   Zadig was never run.
4. **Test signing.** Measured, and it does not even unblock the install. Out.

`[UNVERIFIED]` `ReplaceDevice` as an INF directive to win against a Windows
Update rebind. It is deliberately absent rather than guessed at, because an
unrecognised directive can fail the whole INF.

Evidence gathered: `C:\Windows\INF` on that guest holds 662 `.inf` files and
`findstr /s /i /m ReplaceDevice` matches none of them. The same command does
work on that tree - `AddService` matches `oem2.inf` and `oem3.inf`. So the
negative result is real but narrow: it covers the class INFs in `C:\Windows\INF`,
not the driver packages in the DriverStore, which this guest does not expose at
the path searched.

## 20.5 The Meta SDK assumption, and how to undo the install

`[MEASURED]` from the vendor's own package, `metavision/driver/MetaSAQ.inf`:

- it matches the same hardware ID: `%VID_2CFA&PID_00F3.DeviceDesc%=CyUsb3, USB\VID_2CFA&PID_00F3`
- it registers its own device class, "AR Experience Devices",
  `ClassGUID {bb0697e3-404c-42be-8de0-85710015bd26}`
- it installs a kernel driver of its own, `METAUSB3.sys`, service `CYUSB3`,
  KMDF 1.11, with a `WdfCoInstaller01011.dll` co-installer
- it publishes `DriverGUID {5aa8bb92-30a4-449d-b94e-5b995e862939}`

`[INFERRED]` Our INF and the vendor's INF compete for the same hardware ID, in
different classes. **Install ours on a machine that has never had the Meta SDK.**
That is the assumption the whole driver story rests on, and it is the assumption
the install instructions have to state out loud.

Reverting, once an install exists, `[UNVERIFIED]`: find the published name with
`pnputil /enum-drivers`, then `pnputil /delete-driver oemN.inf /uninstall`,
then unplug and replant the device so Windows re-runs driver selection.

## 20.6 The library itself cross-compiles

`[MEASURED]` On Linux, with `mingw-w64` and libusb 1.0.28 built static for
`x86_64-w64-mingw32`:

```
cmake -S . -B build-win \
      -DCMAKE_TOOLCHAIN_FILE=cmake/toolchain-mingw64.cmake \
      -DMETA2_LIBUSB_ROOT=<prefix with include/libusb-1.0 + lib/libusb-1.0.a>
cmake --build build-win
```

- 27 targets built, 24 Windows executables
- `file` on one: `PE32+ executable for MS Windows 5.02 (console), x86-64`
- imports of `meta2_capture_live.exe`: `KERNEL32.dll`, `msvcrt.dll` only
- no undefined symbols in the linked executable

`[MEASURED]` `nm -u` on libusb's `windows_winusb.o` shows no `SetupDi*` or
`WinUsb*` undefined symbols — only `__imp_LoadLibraryA` and
`__imp_GetProcAddress`. libusb 1.0.28 loads the SetupAPI and WinUSB entry
points at runtime, so the absence of a static SetupAPI import is expected and
not a missing dependency.

`[MEASURED]` `pthread` is gone from the public interface. `include/meta2/os.h`
carries opaque `meta2_mutex_t` / `meta2_thread_t`, `src/os.c` holds both
implementations, and a compile-time size check fails the build if the reserved
storage is smaller than the real OS object on either side.

`[MEASURED]` They have now been executed, against the headset passed through into
the guest. The library opens the device, enumerates it, claims the interface, and
runs the arm sequence.

## 20.7 The QEMU guest is not a usable test bed for the streams

The headset was passed into the guest with QMP:

```
device_add {"id":"meta2usb","driver":"usb-host","hostbus":4,"hostaddr":3,
            "bus":"xhci.0","port":"1"}
```

(`vendorid`/`productid` matching does not attach this device; explicit
`hostbus`/`hostaddr` does.)

`[MEASURED]` What passes through the VM correctly:

```
bcdUSB 0300, one interface, bInterfaceClass 0xff, four bulk-IN endpoints,
wMaxPacketSize 1024  -> descriptors are intact, SuperSpeed link reported
claim_interface: OK
vendor control read (wValue=3 in_len=1): 1   -> control transfers work
arm ok=272 fail=135 (8.57 s)                 -> identical to the Linux arm
```

`[MEASURED]` What does not: **bulk-IN data**. `tools/win_probe.c` walks the
stages separately, and the failure is isolated to bulk transfers:

| configuration | result |
|---|---|
| bulk before arm, 256 B – 65536 B | all `LIBUSB_ERROR_TIMEOUT` (same as Linux) |
| bulk after arm, 256 B, one endpoint at a time | **256 bytes on EP `0x81`, `0x83`, `0x84`** |
| bulk after arm, 65536 B | timeout |
| `meta2_capture_live` queue 1, `warm=7e fast`, read_size 1024 / 4096 / 16384 | `health=NO_DATA`, 0 bytes on every endpoint |
| `meta2_capture_live` queue 8 | access violation `0xC0000005` after warm-up |
| sustained single-endpoint loop, 5 s, 1024 B and 8192 B | `0.00 MB/s`, 5 timeouts each |

`[MEASURED]` `usbmon` on the host proves the URBs really reach the physical
device, so this is not a Windows-side invention:

```
S Bi:4:003:1 -115 65536 <      a 64 KiB bulk-IN is submitted to the device
S Bi:4:003:2 -115 65536 <      ...and on every one of the four endpoints
S Bi:4:003:1 -115 1024 <       C Bi:4:003:1 -2 0     1 KiB reads, cancelled, 0 bytes
```

The 1024-byte submissions repeat every ~3 ms and complete with status `-2`
(unlinked) and zero bytes. QEMU is scheduling the endpoints one max-packet at a
time and giving up on each one.

`[MEASURED]` The same binary, the same arm file, the same device, read directly on
the Linux host, returns data immediately:

```
post-arm EP 0x81 size=256: rc=0 (Success) bytes=256
```

`[INFERRED]` QEMU's `usb-host` + emulated xHCI is the limiter, not `meta2lib` and
not WinUSB. Bulk passthrough through that path schedules a single max-packet per
service interval, which is orders of magnitude below the ~90 MB/s the mono pair
alone needs. The one run that did return 256 bytes on three endpoints is most
plausibly the device sitting in an armed state left by an earlier session - the
device's hysteresis is documented in docs/10 and this fits it.

`[OPEN]` Whether the async crash (`0xC0000005`, queue 8) is a real `meta2lib` bug
or a consequence of the same broken transport is **not established**. It has not
been patched, because there is no working transport here to verify a fix against.

`[OPEN]` The only remaining question - does `meta2lib` stream on a real Windows
host - cannot be answered from this environment. It needs the headset plugged
into a physical Windows machine.

## 20.8 WinUSB cannot do the device reset the startup recipe depends on

`[MEASURED - from source]` libusb 1.0.28 `libusb/os/windows_winusb.c`,
`winusbx_reset_device()`, quoting the Microsoft white paper it is written
against:

```
 * "WinUSB does not support host-initiated reset port and cycle port operations"
 * IOCTL_INTERNAL_USB_CYCLE_PORT is only available in kernel mode and the
 * IOCTL_USB_HUB_CYCLE_PORT ioctl was removed from Vista => the best we can do
 * is cycle the pipes (and even then, the control pipe can not be reset using
 * WinUSB)
```

What the function actually does: `AbortPipe` + `FlushPipe` + `ResetPipe` on every
data endpoint, **never the control pipe**, and then:

```
// libusbK & libusb0 have the ability to issue an actual device reset
if ((sub_api != SUB_API_WINUSB) && (WinUSBX[sub_api].ResetDevice != NULL))
    WinUSBX[sub_api].ResetDevice(winusb_handle);
...
return LIBUSB_SUCCESS;
```

So with the plain WinUSB sub-API - which is what our INF selects - a real device
reset is not attempted at all, and the call still reports success.

`[MEASURED]` On Linux `libusb_reset_device()` is a genuine port reset, and
`meta2_stream_start()`'s gate recovery is built on it: each failed attempt prints
"re-armed from a port reset". On Windows that step resets pipes only.

`[MEASURED]` The shape of a real Windows 11 run fits this exactly. First attempt
arms the way Linux arms:

```
stream: arm ok=289 fail=118 (6.97 s)      <- Linux: 272 ok / 135 fail in 8.5 s
```

Every attempt after the first, all of which went through a "port reset", arms a
different way, identically, five times:

```
stream: arm ok=404 fail=3 (0.65 s)        <- the starved-mode signature measured
stream: arm ok=403 fail=4 (0.70 s)           in docs/10: 403 ok / 4 fail in 0.73 s
stream: arm ok=404 fail=3 (0.64 s)
stream: arm ok=403 fail=4 (0.70 s)
stream: arm ok=404 fail=3 (0.65 s)         all five: bytes mux=0 mono=0 rgb=0 tof=0
```

`[INFERRED]` The device is left in an armed-but-not-producing state, and the gate
has no way to get out of it on Windows, because the one operation it uses to get
out is a no-op there.

`[OPEN]` This explains attempts 2-5. It does **not** explain attempt 1, which
armed in the Linux-like shape after a power cycle and still produced zero bytes.
That half is unresolved.

Candidate fixes, none implemented or tested:
- close and reopen the device handle between attempts, which is the nearest user
  mode equivalent of what a port reset achieves;
- stop relying on reset at all and find a vendor-protocol command that returns
  the device to its post-connect state;
- Windows-side: disable/enable the device node through SetupAPI
  (`DIF_PROPERTYCHANGE`, `DICS_STOP`/`DICS_START`), which does re-initialise a
  device from user mode without a kernel driver.

## 20.9 The Windows 11 machine is on a USB 2.0 port, and SuperSpeed is a hard gate

`[MEASURED]` `tools/win_probe.exe` on the real Windows 11 machine:

```
candidate: bus 2 address 25 speed HIGH 480 Mb/s  class 00 ports: 3
opened:    bus 2 address 25 speed HIGH 480 Mb/s
bcdUSB 0210 device class 00 bNumConfigurations 1
  interface 0 class ff subclass 00 protocol 00 eps 4
    ep 81 attr 02 maxpacket 512 (burst 0) interval 0
    ep 82 attr 02 maxpacket 512 (burst 0) interval 0
    ep 83 attr 02 maxpacket 512 (burst 0) interval 0
    ep 84 attr 02 maxpacket 512 (burst 0) interval 0
```

Against the same device on the Linux host and in the VM: `bcdUSB 0300`,
`wMaxPacketSize 1024`, SuperSpeed 5 Gb/s. So the link negotiated **USB 2.0 High
Speed**, and the device presented its USB 2 descriptor set.

`[MEASURED]` `ports: 3` is a single port number, so the device sits directly on a
root hub port - no hub in between. The limitation is the port or the cable.

`[VERIFIED, already in docs/12 §12.29 and docs/14]` This is not a new
constraint. `meta2_host_impl.dll` gates on it explicitly: it tests byte `+0x979`
on the device object (the CyAPI SuperSpeed flag) and its `.rdata` carries
`Device not connected in SuperSpeed mode.` and `Please reconnect device to a
SuperSpeed port.` docs/12 also records that the physical PC's own diagnostics app
reported the headset on a USB 2.0 port. docs/15 item 10 lists it as `[VERIFIED]`.

`[MEASURED]` The bandwidth makes it decisive regardless of the gate. Full stream
at measured cadences:

| endpoint | bytes/frame | frames/s | Mb/s |
|---|---|---|---|
| mono pair (`0x82`) | 721,952 × 2 | 60 each | 693 |
| RGB (`0x83`) | 1,843,232 | 30 | 442 |
| mux (`0x81`) | 256 | ~1000 | 2 |
| **total** | | | **~1137 Mb/s ≈ 142 MB/s** |

USB 2.0 High Speed is 480 Mb/s raw. The mono pair alone does not fit.

`[INFERRED]` Zero bytes on *every* endpoint, including the tiny mux, is consistent
with a device that will not start its streaming engine on a link that cannot
carry it. Whether the device refuses or merely degrades has not been measured -
it has never been observed at High Speed on Linux.

`[OPEN]` This supersedes the transport question. Until the headset is on a
SuperSpeed port on that machine, nothing about `meta2lib`'s Windows bulk path can
be evaluated, and the port-reset finding in 20.8 is not yet the binding
constraint.

### 20.9.1 Corrected the same day: SuperSpeed was necessary, not sufficient

`[MEASURED]` The headset was moved to a SuperSpeed port and `win_probe` re-run:

```
opened: bus 2 address 32 speed SUPER 5 Gb/s
bcdUSB 0300
  ep 81..84 attr 02 maxpacket 1024 (burst 0)
claim_interface 0: 0        vendor control read: rc=1
arm ok=272 fail=135 (8.16 s)
```

The descriptors now match Linux exactly, and the arm is the fresh Linux shape -
`272 ok / 135 fail`, against Linux's `272 / 135 in 8.5 s`. Bulk-IN still returns
zero bytes on all four endpoints, at every stage: before arm, after arm, sustained
4 KiB loop, after reset, and after close + reopen + re-arm. All `rc=-7` timeouts.

`[MEASURED]` So the USB 2 link was a real defect and it is fixed, but it was not
the cause of the no-data condition. The claim in 20.9 that this "supersedes the
transport question" was wrong, and is withdrawn.

`[MEASURED]` `meta2_stream_demo.exe` on the SuperSpeed port arms `400 ok / 7 fail`
on its first attempt and `403 / 4` on every later one, with zero bytes - the
starved shape, and the same five times in a row, because the gate's reset is a
no-op (20.8).

#### Bulk-IN works on real Windows 11 - the transport is not the blocker

`[MEASURED]` A later `win_probe` run on the same SuperSpeed port:

```
pre-arm  EP 0x81 size=1024: rc=-7 bytes=0 waited=3004 of 3000 ms   (all four eps)
arm ok=272 fail=135 (8.21 s)
post-arm EP 0x81 size=1024: rc=0  bytes=256  waited=0 of 3000 ms
post-arm EP 0x82 size=1024: rc=0  bytes=1024 waited=0
post-arm EP 0x83 size=1024: rc=0  bytes=1024 waited=0
post-arm EP 0x84 size=1024: rc=0  bytes=1024 waited=0
sustained EP 0x81 size=4096: 0.00 MB/s reads=3  timeouts=5
sustained EP 0x82 size=4096: 0.00 MB/s reads=3  timeouts=5
sustained EP 0x83 size=4096: 0.01 MB/s reads=15 timeouts=5
sustained EP 0x84 size=4096: 0.01 MB/s reads=15 timeouts=5
pending-before-arm, 65536 B URBs, all four endpoints: 0 B, first_data=none
```

`[MEASURED]` So WinUSB on this machine does deliver bulk-IN data, immediately
(`waited=0`), on all four endpoints, right after the arm. The earlier "Windows
bulk transport does not work" reading is dead.

`[MEASURED]` It is a trickle, not a stream: 0.01 MB/s against the 55 MB/s an RGB
endpoint emits in a healthy session. The device is in a starved state, not a
healthy one.

`[MEASURED]` `waited=3004 of 3000 ms` on every failure: libusb's own timeout is
what ends these reads. No shorter host-side timeout is firing, so the HCTimeout
idea is dead as an explanation.

`[MEASURED]` Requests already outstanding when the arm lands receive nothing
(`first_data=none`), while a request issued after the arm receives data at once.
That is the opposite of the Linux recipe, which requires readers pending before
the arm.

#### The device needs ~7.7 s of continuously outstanding IN requests

`[MEASURED]` The pending-before-arm stage with 65536-byte URBs, on real Windows
11 at SuperSpeed:

```
arm (with IN pending) ok=269 fail=138 (8.35 s)
pending EP 0x81: 126,976 B    completions=498 timeouts=1  first data after    1 ms
pending EP 0x82: 44,957,696 B completions=688 timeouts=1  first data after 7718 ms
pending EP 0x83: 29,360,128 B completions=450 timeouts=1  first data after 7709 ms
pending EP 0x84: 20,447,232 B completions=314 timeouts=1  first data after 7649 ms
```

`[MEASURED]` Four independent endpoints agreed on when the first byte arrived:
7649, 7709, 7718, 7775 ms - a 126 ms spread. The 1024-byte variant produced
exactly one 1024-byte completion per endpoint at 7718-7775 ms and then nothing,
so a large URB is what sustains production once it starts.

`[MEASURED]` `meta2lib`'s readers used a 1500 ms bulk timeout in both the sync
loop and the async queue. 1500 ms is a fifth of what the device asks for, and on
Windows an expired transfer is a `WinUsb_AbortPipe`, not an unlink. That is the
first explanation that accounts for the library failing while the probe succeeds
with the same handle, same endpoints, same arm.

`[MEASURED]` `meta2_capture_live.exe ... 14 1 150 1024 warm=7e fast gate tries=3`
still produced zero bytes with 18 timeouts per endpoint - so URB size alone is
not the answer, and the timeout is the remaining difference.

#### The 7.7 s startup is real, and warm/sustain and 0x84 are ruled out

`[MEASURED]` `ONLY_PENDING=1` runs the pending stage in a fresh process with
nothing before it. Reproduced, near-identically, against the earlier run:

| endpoint | fresh process | earlier run | first byte |
|---|---|---|---|
| `0x81` mux | 128,768 B / 506 | 126,976 B / 498 | 1 ms |
| `0x82` mono | 45,940,736 B / 704 | 44,957,696 B / 688 | 7716 ms |
| `0x83` RGB | 28,573,696 B / 439 | 29,360,128 B / 450 | 7713 ms |
| `0x84` ToF | 20,840,448 B / 321 | 20,447,232 B / 314 | 7653 ms |

`[MEASURED]` So the ~7.7 s first-byte latency is a startup property, not
hysteresis left by earlier stages. It reproduced within 63 ms across processes.

`[MEASURED]` Ruled out as the reason the library fails, each by a run that still
produced zero bytes: the 4 s warm assert, the sustain loop (`nosustain`), whether
`0x84` is serviced (`tof`), URB size (1024 and 65536), and the bulk timeout
(`rd_ms=10000`, visible as timeouts falling from 18 to 4 per endpoint).

`[MEASURED]` Two differences between the working probe and the failing library
are left. `meta2_open()` calls `libusb_set_configuration(h, 1)`, and libusb's
Windows backend implements that as a real control request to the device -
`winusb_set_configuration()` at `windows_winusb.c:2126` sends
`OUT | STANDARD | DEVICE, SET_CONFIGURATION, wValue=config` with a 1000 ms
timeout. The probe never sends it. And `meta2_capture_live` additionally does
`meta2_reset(); meta2_close(); sleep 2 s; meta2_open()` at its start, which on
Windows is the AbortPipe/FlushPipe/ResetPipe sequence of 20.8. The second
remaining difference is reader shape: the probe uses async transfers pumped by one
thread, the library at `queue=1` uses synchronous reads on three or four threads.

#### The open path is what killed it

`[MEASURED]` `LIB_OPEN=1` makes the probe open the device the way `meta2_open()`
does and changes nothing else - same pending URBs submitted before any control

`[UNEXPLAINED]` Why. libusb's Windows event loop waits on `WaitForMultipleObjects`
over a per-context handle array (`os/events_windows.c:167-175`), one handle for the
internal signalling event and one for the timer, rather than on per-transfer
objects, so two callers share and consume the same signalling event. That is
consistent with the observation and is the best candidate, but nothing measured
here proves it is the mechanism. What is proven is the rule, not the cause.

`[MEASURED]` The rule, and the shape the library now implements: **open -> claim
-> submit the IN transfers -> arm with no other thread pumping -> start the pump.**
`meta2_reader_submit_async()` and `meta2_pump_start()` exist to make that ordering
expressible; `meta2_capture_live` uses it at `queue>1`. The synchronous readers
used at `queue=1` cannot satisfy it, because a synchronous read pumps events on
its own thread - which is why `queue=1` has produced zero bytes on Windows in
every configuration tried.

`[MEASURED]` A separate bug found in the harness while doing this: at `queue>1`
`meta2_capture_live` handed `bmon`/`brgb`/`bmux` to the async readers as their
rings and then drained them, which memmoved each reader's unread tail to the
front of the same buffer and wrote the drained copy back over it. Two writers in
one buffer. `queue=1` never reached it because no bytes arrived; `queue=8` died
silently, which is what that looked like.

`[MEASURED]` A second, separate Windows bug: at `queue=8` the run printed the arm
and then nothing at all - the process died silently, the same failure as the
`0xC0000005` access violation seen at queue=8 in the VM. Cause in source: every
async reader started its own `libusb_handle_events()` thread on the one shared
context, and libusb delivers a completion to whichever thread is pumping rather
than to the thread that submitted, so one reader's pump could run another
reader's callback after its state had been freed.

Both are fixed in `meta2lib` as of this commit: `meta2_open()` asks for
configuration 1 only when the device is not already in it, and the async readers
share one refcounted event pump.

### The bogus mux counter is `0xFEEDBAAB` — the record's own frame magic

`[MEASURED]` The diagnostic named the records, and they are not corruption. Counter sequences run:

```
609582 -> 4276992683 -> 609584      (tag 102, i=23168)
648332 -> 4276992683 -> 648334      (tag 119, i=26770)
629766 -> 0          -> 629768      (tag 119, i=8520)
```

`4276992683 = 0xFEEDBAAB`, which is the low word of `MUX_MAGIC` — the record header is
`00 00 00 00 ab ba ed fe`, and bytes +4..+7 read little-endian as exactly that. **The counter
slot at +252 holds the frame magic.** The value reappeared verbatim across separate runs, and
the counter sequence continues straight through the record, so it is a marker-shaped record,
not a damaged sample.

`[MEASURED]` There are only two to four of them per window of 34,033 or 66,764 records — but
`counter_span` is a min/max, so they own it: spans of 4,276,992,683 and 4,276,406,310 for
windows of ~17,000 records. `[FIXED]` `META2_MUX_COUNTER_SENTINEL` is now excluded from the
span, and `outliers=N` is printed.

### The run hung at teardown, and it was a library bug

### What `coverage` actually measures (do not retune the constant)

`[MEASURED]` `coverage = median(consecutive mux timestamp delta) x record rate /
META2_MUX_CLOCK_HZ`, and `META2_MUX_CLOCK_HZ` is **183 MHz**, not the calibrated
tick rate of 117,821,900 Hz. That is deliberate and documented in
`include/meta2/health.h`: the constant is a proxy for the median-delta estimator,
the 0.85 threshold was tuned against that same estimator, and healthy Linux runs
measured **0.99-1.01** with it. Changing the constant without re-measuring the
threshold moves the gate blind.

`[MEASURED]` The estimator is burst-sensitive: it reads the typical *within-burst*
spacing, so a session that delivers in clusters scores low even when its min/max
span covers the window. In the starved attempt the span was 146.35 MHz x window
(124% of it) while coverage read 0.1001. Both numbers are correct; they measure
different things, and the span is the one that misleads on a clustered run.

`[OPEN]` The fix is now a knob, not yet a proven default: `meta2_set_bulk_timeout()`
and `META2_BULK_TIMEOUT_MS`, default still 1500 because every Linux measurement
was made at 1500. `rd_ms=10000` has to be measured on the real machine before the
default changes, and the Linux side has to be re-measured after it.

`[MEASURED]` A separate Windows hazard seen in the same run: the device
re-enumerates spontaneously (bus address went 25 → 32 → 40 → 53 → 55 across runs,
and 53 → 55 inside one run). A handle opened before that is dead - the control
read returned `rc=-9` and every bulk read then returned `rc=-1` immediately with
`waited=0`. The library has no reopen path for that yet.

`[OPEN]` Throughput is not yet full rate. The probe keeps one URB outstanding per
endpoint, so 688 completions in ~12.6 s is latency-limited at ~3.6 MB/s against
the 86 MB/s the mono pair emits in a healthy session. Depth is needed, and depth
is where the queue-8 access violation lives.

| | pending before arm | 65536-byte URB |
|---|---|---|
| probe post-arm | no | **never tested** - the loop stops at the first success |
| probe pending stage | yes | yes → 0 B |
| `meta2_capture_live` / `meta2_stream_demo` | yes | yes → 0 B |

`win_probe` now tests the two empty cells: post-arm with a 65536-byte URB alone,

## The fixed estimator on real runs — and the two holes in the gate

Four runs on 2026-10-27 against `meta2lib ee397c1`. All four commands were the
ones proposed to test the estimator fix.

| command | est | zero_deltas | cov_cal | steady mux | verdict |
|---|---|---|---|---|---|
| `mux=1f muxhz=100 muxkeep` | `imu` | 0.02 | **0.9906** | 2,544/s | `health=OK`, no override |
| `mux=1b muxhz=100 muxkeep` | `imu` | 0.01 | **0.9834** | 398/s | `health=OK`, no override |
| no `muxasync`, `tries=1` | `imu` | 0.00 | 0.4454 | **7/s** | FROZEN - and silently accepted |
| `mux=4 muxhz=100 muxkeep` | `imu` | 0.00 | 0.3108 | 2,181/s | FROZEN - and silently accepted |

The estimator fix is confirmed on the first two. `est=imu` selected exactly
IMU0+IMU1 (16,793 and 17,194 records, matching the tag counts), `zero_deltas`
fell from 0.42 to 0.02, `cov_cal` landed at 0.99 and 0.98, and **no `gate
override` line printed** - the estimator accepted them on its own. That absence
was the point of the test.

### Hole 1: `tries=1` switched the override off entirely

The override lived inside `if (g_gate && trying < g_maxtries && ...)`. On the
last attempt `trying == g_maxtries`, so the whole block - override included -
was skipped. `tries=1` therefore disabled the override completely.

The consequence was not a missing line, it was a wrong reading in both
directions: the `mux=0x04` session at 2,181 records/s looked rejected, and the
no-`muxasync` session at **7 records/s** looked accepted. Neither printed
anything saying which had happened.

### Hole 2: a completed-but-rejected final attempt printed no warning

The `WARNING: all N attempts were rejected` line was only reachable when the
window had been truncated (`aborted`). A window that ran to completion and was
still FROZEN printed `gate verdict:` and then the full mono/RGB analysis, which
read as a healthy capture.

Both fixed: one verdict, printed once, for every attempt count -
`gate: ACCEPTED by the estimator` / `ACCEPTED on the measured rate` /
`WARNING: gate REJECTED this session`. The override is a judgement about the
session, not about which attempt it was.

### coverage measures uniformity, not rate

`coverage = median(timestamp delta) x records/s / clock` is invariant under
throttling: halve the rate and the spacing doubles, so the product is unchanged.
A synthetic mux at 100 records/s - 38% of the 260/s floor - scores
`cov_cal 1.0000` and `health=OK`. Locked as a test.

So `cov_cal=OK` proves the timestamps are self-consistent with the calibrated
oscillator and proves nothing about rate. The 7 records/s run was caught only
because its spacing was irregular (`cov_cal 0.445`), not because it was slow.
A uniformly-throttled mux would pass the estimator and can only be caught by
the measured steady rate. Both checks are load-bearing.

### The mux submask gates each feed's rate separately

| submask | feeds asserted | steady mux | IMU pair | MICS |
|---|---|---|---|---|
| `0x1b` | Imu0, Imu1, ToF, Mux | 398/s | ~400/s | backlog only (16,727) |
| `0x1f` | + Mics | 2,544/s | ~400/s | ~2,150/s |
| `0x04` | Mics only | 2,181/s | ~0/s after the backlog | ~2,180/s |

`0x1f` steady (2,544) is `0x1b` steady (398) plus the mic feed - the feeds add.
`mux=0x04` is the informative one: with only the Mics bit sustained, the IMU
feeds stop once the arm backlog drains. Their 6,122 records are backlog, and
their timestamps span only 8.03 s of a 25 s window, which is why `cov_cal`
reads 0.31 there. That is the estimator being correct, not broken.

Backlog is large and consistent: ~26,000 mux records (~10 s at 2,550/s) were
queued device-side at 125 min uptime, and the cameras never dropped a byte
while it drained.
