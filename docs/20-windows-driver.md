# 20. Running `meta2lib` on Windows

Status of the Windows side, and the one thing that currently blocks it.

Everything marked `[MEASURED]` was run and its output kept. Everything marked
`[INFERRED]` is reasoning from that evidence. `[UNVERIFIED]` means it is a plan
that has not been executed anywhere.

---

## 20.1 What the device needs before any program can open it

`[MEASURED]` from `lsusb -v -d 2cfa:00f3`:

| property | value |
|---|---|
| `idVendor` / `idProduct` | `0x2cfa` / `0x00f3` |
| interfaces | one |
| `bInterfaceClass` | `0xFF` (vendor-specific) |
| `bInterfaceSubClass` / `bInterfaceProtocol` | `0x00` / `0x00` |
| endpoints | four bulk-IN, **no bulk OUT** |
| link speed | SuperSpeed, 5 Gbps |

`[MEASURED]` The device does **not** implement Microsoft OS descriptors.
`tools/msos_probe.c` (build: `gcc msos_probe.c -o msos_probe $(pkg-config --cflags --libs libusb-1.0)`):

```
string 0xEE: FAILED LIBUSB_ERROR_PIPE
MS OS compat ID: FAILED LIBUSB_ERROR_PIPE
MS OS 2.0 compat ID: FAILED LIBUSB_ERROR_PIPE
iProduct: Meta2
```

The ordinary string descriptors answer normally, so the control endpoint works;
the STALLs are specific to the MS OS feature.

That matters because MS OS descriptors are the mechanism by which a
vendor-specific device gets WinUSB installed by Windows with no INF, no catalog
and no signature prompt. This device does not have them.

`[INFERRED]` No in-box Windows driver matches a single vendor-specific
interface, so on a machine that has never had the Meta SDK the device arrives
with no driver at all. A driver package has to be supplied.

`[INFERRED]` Because there is one interface, the function driver binds to the
device directly. `usbccgp`, which exists to split composite devices into
per-interface children, is not involved.

---

## 20.2 The driver package we wrote

`meta2lib/driver/meta2.inf`. It installs **Microsoft's own `WinUSB.sys`** as the
function driver for `USB\VID_2CFA&PID_00F3`.

It ships no binary. Every file it installs is already inside Windows and already
signed by Microsoft, so nothing of ours runs in kernel space.

Shape:

- `Class = USB`, `ClassGuid = {36fc9e60-c465-11cf-8056-4445bc7c5199}`
- `AddService = WinUSB, 0x00000002, ...` — the `0x2` is
  `SPSVCINST_ASSOCSERVICE`, the flag that actually associates the service with
  the device node. Without it WinUSB is installed as a service and is not the
  device's function driver.
- `ServiceBinary = %12%\WinUSB.sys` — the in-box driver.
- `DeviceInterfaceGUIDs = {c0ee1632-92f8-44a1-bcff-6013a2369925}`, fixed so a
  native WinUSB client can open the device by GUID. `libusb` does not need it.
- `PnpLockdown = 1` so a class driver cannot silently take the interface back.
- No `CatalogFile` line. A catalog signs the binaries a package installs; this
  package installs none of its own. Referencing a catalog that is not shipped
  fails the install outright, which is worse than a warning.

## 20.3 The blocker, and the way through it: a signed catalog

`[MEASURED]` Windows 10 1809 x64 guest, administrator shell, test signing off:

```
pnputil /add-driver meta2.inf /install
Adding driver package:  meta2.inf
Failed to add driver package: The third-party INF does not contain digital
signature information.
Total driver packages:  1
Added driver packages:  0
```

`[MEASURED]` Test signing does **not** lift this. After `bcdedit /set testsigning
on`, a reboot, and `bcdedit /enum` confirming `testsigning Yes`, the same command
gave the same refusal. The plan of "ship an unsigned INF and tell users the
warning is harmless" is dead on x64 Windows: there is no warning to accept.

`[MEASURED]` SetupAPI's own log (`C:\Windows\INF\setupapi.dev.log`) shows the INF
is otherwise fine - it parses, matches the hardware ID, and is selected as the
best driver. Only the catalog step fails. Two distinct failure codes were
measured:

| condition | code |
|---|---|
| no catalog at all | `0xE000022F` |
| catalog present, but it does not contain the INF's own hash | `0xE000024B` |

`[MEASURED]` The second one is the interesting one. A catalog that hashes only
"the files the package installs" is not enough, because this package installs no
files - the catalog has to hash **the INF itself**. `driver/meta2_mkcat.c` does
exactly that with `CryptCATAdminCalcHashFromFileHandle` +
`CryptCATPutMemberInfo` + `CryptCATPutAttrInfo` + `CryptCATPersistStore`, all
from `wintrust.dll`. No WDK, no `Inf2Cat.exe`, no `makecat.exe` - a probe of the
guest found none of the WDK tools present.

`[MEASURED]` Signing is a throwaway certificate, installed into the machine's own
trust stores, in the same shape libwdi/Zadig uses:

```
cert: "CN=usb\vid_2cfa&pid_00f3 (meta2lib autogenerated)"
      thumbprint F8671468EE2030E503962158D6DD2CDE13E4A73E
installed into LocalMachine\Root and LocalMachine\TrustedPublisher
Set-AuthenticodeSignature -> Valid : Signature verified.
private key destroyed
catalog now: Valid
```

`[MEASURED]` With that catalog, the committed INF installs and binds:

```
pnputil /add-driver C:\Users\hermes\driver\meta2.inf /install
Driver package added successfully.
Published Name:         oem3.inf
Driver package installed.

instance:  USB\VID_2CFA&PID_00F3\5&134707B&0&1
friendly:  Meta 2 AR headset (meta2lib / WinUSB)
status:    OK   problem: CM_PROB_NONE
driver:    {36fc9e60-c465-11cf-8056-444553540000}\0002   inf: oem3.inf
WinUSB service: Running
```

`[MEASURED]` One INF bug was in the way until it was fixed. The class GUID tail
`{36fc9e60-c465-11cf-8056-4445bc7c5199}` - the one that appears in a great many
INF examples - is wrong for this purpose and the install fails with it. The USB
class GUID Windows itself uses ends `{36fc9e60-c465-11cf-8056-444553540000}`.

`[MEASURED]` The vendor driver is real competition: `MetaReader` stages a package
signed `Signer Name: Meta Company` that binds the same hardware ID. Our INF is
dated 2026 against the vendor's 2016, and driver rank picks the newer one, which
is why the device switched without any manual unbind.

## 20.4 What this means for distribution

`[MEASURED]` The self-signed catalog route works **on the machine it was run on**,
because the certificate was placed into that machine's `Root` and
`TrustedPublisher` stores. That is the whole trick, and it is the same trick
libwdi/Zadig plays. It is a development unlock, not a distribution story: nobody
else's machine has that certificate.

`[MEASURED]` Zadig itself was inspected rather than trusted. `zadig.c` (2141
lines, the GUI) contains no command-line handling at all; `wdi-simple.c` is the
scriptable sample libwdi ships. libwdi 1.5.1 source was unpacked and read: the
catalog is built through `wintrust.dll` and signed through `mssign32.dll` with a
throwaway certificate, which is what `driver/meta2_mkcat.c` and
`driver/install-driver.ps1` reproduce.

So the distribution decision is now concrete rather than open:

1. **A real Authenticode certificate.** Sign `meta2.cat`, ship `meta2.inf` +
   `meta2.cat`, one `pnputil` line, no user-visible warning. This is the only
   route that a normal user can complete. Cost and enrolment sit outside the
   repository. `[UNVERIFIED]`
2. **Microsoft attestation signing.** The guest's driver store shows what its
   output looks like: `Signer Name: Microsoft Windows Hardware Compatibility
   Publisher` on the USBPcap package. Needs a Partner Center account.
   `[UNVERIFIED]`
3. **Ship the Zadig/libwdi installer** and let it do the same thing we did here.
   Works, adds a third-party dependency and a GUI step. `[UNVERIFIED]` here -
   Zadig was never run.
4. **Test signing.** Measured, and it does not even unblock the install. Out.

`[UNVERIFIED]` `ReplaceDevice` as an INF directive to win against a Windows
Update rebind. It is deliberately absent rather than guessed at, because an
unrecognised directive can fail the whole INF.

Evidence gathered: `C:\Windows\INF` on that guest holds 662 `.inf` files and
`findstr /s /i /m ReplaceDevice` matches none of them. The same command does
work on that tree - `AddService` matches `oem2.inf` and `oem3.inf`. So the
negative result is real but narrow: it covers the class INFs in `C:\Windows\INF`,
not the driver packages in the DriverStore, which this guest does not expose at
the path searched.

## 20.5 The Meta SDK assumption, and how to undo the install

`[MEASURED]` from the vendor's own package, `metavision/driver/MetaSAQ.inf`:

- it matches the same hardware ID: `%VID_2CFA&PID_00F3.DeviceDesc%=CyUsb3, USB\VID_2CFA&PID_00F3`
- it registers its own device class, "AR Experience Devices",
  `ClassGUID {bb0697e3-404c-42be-8de0-85710015bd26}`
- it installs a kernel driver of its own, `METAUSB3.sys`, service `CYUSB3`,
  KMDF 1.11, with a `WdfCoInstaller01011.dll` co-installer
- it publishes `DriverGUID {5aa8bb92-30a4-449d-b94e-5b995e862939}`

`[INFERRED]` Our INF and the vendor's INF compete for the same hardware ID, in
different classes. **Install ours on a machine that has never had the Meta SDK.**
That is the assumption the whole driver story rests on, and it is the assumption
the install instructions have to state out loud.

Reverting, once an install exists, `[UNVERIFIED]`: find the published name with
`pnputil /enum-drivers`, then `pnputil /delete-driver oemN.inf /uninstall`,
then unplug and replant the device so Windows re-runs driver selection.

## 20.6 The library itself cross-compiles

`[MEASURED]` On Linux, with `mingw-w64` and libusb 1.0.28 built static for
`x86_64-w64-mingw32`:

```
cmake -S . -B build-win \
      -DCMAKE_TOOLCHAIN_FILE=cmake/toolchain-mingw64.cmake \
      -DMETA2_LIBUSB_ROOT=<prefix with include/libusb-1.0 + lib/libusb-1.0.a>
cmake --build build-win
```

- 27 targets built, 24 Windows executables
- `file` on one: `PE32+ executable for MS Windows 5.02 (console), x86-64`
- imports of `meta2_capture_live.exe`: `KERNEL32.dll`, `msvcrt.dll` only
- no undefined symbols in the linked executable

`[MEASURED]` `nm -u` on libusb's `windows_winusb.o` shows no `SetupDi*` or
`WinUsb*` undefined symbols — only `__imp_LoadLibraryA` and
`__imp_GetProcAddress`. libusb 1.0.28 loads the SetupAPI and WinUSB entry
points at runtime, so the absence of a static SetupAPI import is expected and
not a missing dependency.

`[MEASURED]` `pthread` is gone from the public interface. `include/meta2/os.h`
carries opaque `meta2_mutex_t` / `meta2_thread_t`, `src/os.c` holds both
implementations, and a compile-time size check fails the build if the reserved
storage is smaller than the real OS object on either side.

`[MEASURED]` They have now been executed, against the headset passed through into
the guest. The library opens the device, enumerates it, claims the interface, and
runs the arm sequence.

## 20.7 The QEMU guest is not a usable test bed for the streams

The headset was passed into the guest with QMP:

```
device_add {"id":"meta2usb","driver":"usb-host","hostbus":4,"hostaddr":3,
            "bus":"xhci.0","port":"1"}
```

(`vendorid`/`productid` matching does not attach this device; explicit
`hostbus`/`hostaddr` does.)

`[MEASURED]` What passes through the VM correctly:

```
bcdUSB 0300, one interface, bInterfaceClass 0xff, four bulk-IN endpoints,
wMaxPacketSize 1024  -> descriptors are intact, SuperSpeed link reported
claim_interface: OK
vendor control read (wValue=3 in_len=1): 1   -> control transfers work
arm ok=272 fail=135 (8.57 s)                 -> identical to the Linux arm
```

`[MEASURED]` What does not: **bulk-IN data**. `tools/win_probe.c` walks the
stages separately, and the failure is isolated to bulk transfers:

| configuration | result |
|---|---|
| bulk before arm, 256 B – 65536 B | all `LIBUSB_ERROR_TIMEOUT` (same as Linux) |
| bulk after arm, 256 B, one endpoint at a time | **256 bytes on EP `0x81`, `0x83`, `0x84`** |
| bulk after arm, 65536 B | timeout |
| `meta2_capture_live` queue 1, `warm=7e fast`, read_size 1024 / 4096 / 16384 | `health=NO_DATA`, 0 bytes on every endpoint |
| `meta2_capture_live` queue 8 | access violation `0xC0000005` after warm-up |
| sustained single-endpoint loop, 5 s, 1024 B and 8192 B | `0.00 MB/s`, 5 timeouts each |

`[MEASURED]` `usbmon` on the host proves the URBs really reach the physical
device, so this is not a Windows-side invention:

```
S Bi:4:003:1 -115 65536 <      a 64 KiB bulk-IN is submitted to the device
S Bi:4:003:2 -115 65536 <      ...and on every one of the four endpoints
S Bi:4:003:1 -115 1024 <       C Bi:4:003:1 -2 0     1 KiB reads, cancelled, 0 bytes
```

The 1024-byte submissions repeat every ~3 ms and complete with status `-2`
(unlinked) and zero bytes. QEMU is scheduling the endpoints one max-packet at a
time and giving up on each one.

`[MEASURED]` The same binary, the same arm file, the same device, read directly on
the Linux host, returns data immediately:

```
post-arm EP 0x81 size=256: rc=0 (Success) bytes=256
```

`[INFERRED]` QEMU's `usb-host` + emulated xHCI is the limiter, not `meta2lib` and
not WinUSB. Bulk passthrough through that path schedules a single max-packet per
service interval, which is orders of magnitude below the ~90 MB/s the mono pair
alone needs. The one run that did return 256 bytes on three endpoints is most
plausibly the device sitting in an armed state left by an earlier session - the
device's hysteresis is documented in docs/10 and this fits it.

`[OPEN]` Whether the async crash (`0xC0000005`, queue 8) is a real `meta2lib` bug
or a consequence of the same broken transport is **not established**. It has not
been patched, because there is no working transport here to verify a fix against.

`[OPEN]` The only remaining question - does `meta2lib` stream on a real Windows
host - cannot be answered from this environment. It needs the headset plugged
into a physical Windows machine.

## 20.8 Open items

1. Run a cross-built harness on real Windows with the headset attached, and
   re-tune `meta2_stream_start()` for the Windows host. The startup recipe is
   empirical and the hysteresis is not understood; a different host controller
   and driver stack may need different gate settings. **This is now the first
   item, because the VM cannot answer it.**
2. A distribution signing route for `meta2.inf`. The install itself is solved;
   who signs the catalog is not (see 20.4).
3. Whether Windows Update rebinds `USB\VID_2CFA&PID_00F3` on Windows 11, and
   what actually wins if it does.
4. The async reader crash under queue 8 on Windows, once there is a transport
   that can show whether it is real.
5. The GUI, which is the end goal, is not started.
6. `ReplaceDevice` syntax, and whether it is even the right mechanism against a
   Windows 11 rebind.
